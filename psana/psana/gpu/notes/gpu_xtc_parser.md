# GPU XTC parser

Status: the detector-independent Configure schema compiler, the one-thread
byte-stream indexer, the one-thread-per-dgram XTC walker, lazy GPU field
decoder, and isolated KvikIO correctness driver are implemented. A
cooperative warp/block parser is still a design to benchmark against this
baseline.

## Goal and current boundary

The goal is to let a GPU locate and interpret values after raw XTC bytes have
arrived in GPU VRAM. The CPU should not have to parse every event merely to
tell the GPU where detector arrays are.

The current prototype deliberately stays outside the `DataSource` path:

```text
CPU: read and parse the leading Configure dgram once
  -> export Configure Names metadata
  -> compile strings and field definitions into numeric schema tables
  -> upload those tables to the GPU

KvikIO: read a contiguous range after Configure directly into GPU memory
  -> GPU index_dgrams finds complete dgrams in the byte range
  -> GPU walk_xtc finds every ShapesData record in every indexed dgram
  -> gpudgram.get(detname, segment, algname) selects a Configure schema
  -> GPU decode_fields joins ShapesData to that schema and locates fields
  -> an optional CPU parser checks the result
```

This is not a GPU clone of the Python `Dgram` object model. It does not build
nested Python objects or NumPy arrays. Its useful result is a compact field
locator containing type, shape, byte count, and an offset into the original
GPU byte buffer. `GpuFieldView.array` is then a zero-copy CuPy view over that
range.

The code is detector-independent. Detector, algorithm, and field names come
from Configure; there are no Jungfrau, CSPAD, or other detector-specific
keywords in the parser.

## Source map

- `psana/psana/gpu/gpudgram/schema.py`: Configure schema compiler and packed
  schema layouts.
- `psana/psana/gpu/gpudgram/parser.py`: `GPUDgramBatch`, Python-facing views,
  and the three CUDA kernels.
- `psana/psana/gpu/gpudgram/__init__.py`: public imports.
- `psana/psana/gpu/scripts/gpudgram_driver.py`: isolated KvikIO correctness
  driver.
- `psana/src/dgram.cc`: CPU Configure export and event descriptor oracle.
- `psana/psana/tests/gpu/unit/test_gpudgram.py`: schema unit tests.

The three CUDA entry points are generated by `_kernel_source()` in
`parser.py`:

```text
index_dgrams   one thread walks consecutive dgrams in the input byte stream
walk_xtc       one thread per indexed dgram walks the XTC tree
decode_fields  one thread per allocated ShapesData-reference slot decodes a
               matching ShapesData record
```

## XTC schema model

Configure dgrams contain `Names` records. Later dgrams contain `ShapesData`
records. A `ShapesData` record carries a `NamesId` in its XTC `src`; that ID
joins event data to its Configure definition:

```text
Configure Names(NamesId)
  -> detector name/type/id, segment, algorithm/version
  -> ordered field names, types, element sizes, and ranks

Event ShapesData.src
  -> the same NamesId
  -> Shapes child: runtime dimensions for array fields
  -> Data child: field bytes concatenated in Configure field order
```

Detector name, segment, and algorithm name are not repeated as strings in an
event `ShapesData`. They are found by using its `NamesId` to select the
Configure `Names` record. A `NamesId` is encoded as:

```text
names_id_value = (node_id << 8) | local_names_id
```

For example, `0x10c` means node ID 1 and local names ID 12.

Array dimensions are event data rather than a universal Configure constant.
Configure says that a field has rank `r` and which `Shape` row describes it;
the `Shapes` child supplies the dimensions for the current event. Scalars
have rank zero and consume no Shape row.

## What is built from Configure on the CPU

The driver reads only the leading Configure dgram with the existing CPU
`dgram.Dgram` implementation. Internally that object owns the trusted C++
`NamesLookup`/`NameIndex` representation.

Two methods exposed by `dgram.cc` support this prototype:

- `config.config_names()` exports every valid Configure `Names` entry as
  ordinary Python dictionaries. Each entry includes detector identity,
  algorithm identity, segment, the packed and split NamesId, and ordered field
  metadata.
- `event.raw_descriptors(...)` walks an event with the CPU implementation and
  returns its resolved field offsets, sizes, types, and shapes. It is called
  only by the driver after GPU parsing to verify the GPU result.

`GpuNamesSchema.from_config(config)` consumes `config_names()` and builds the
run-scoped CPU object used by the prototype. It retains:

- `NamesSchema` and `FieldSchema` objects with human-readable strings;
- `det_keys`, `alg_keys`, and `field_keys` dictionaries;
- `_by_selector[(det_name, segment, alg_name)]`, whose value can contain one
  or more candidate `NamesSchema` objects;
- two packed `uint64` NumPy tables, `names_table` and `fields_table`.

The keys are generated at runtime by sorting the unique strings
lexicographically and numbering them from zero. They are not values stored in
the XTC file and are not hashes. The reverse mapping therefore remains in the
CPU `GpuNamesSchema`. For the example below:

```text
det_key   4 -> xppcspad
alg_key   3 -> raw
field_key 9 -> arrayRaw
field_key 17 -> floatPgp
```

The packed Names table has six columns:

```text
[NamesId, segment, det_key, alg_key, first_field, n_fields]
```

The packed field table has five columns:

```text
[field_key, type, element_size, rank, shape_index]
```

`shape_index` is consecutive among array fields within one Names entry.
Scalars store `UINT64_MAX` as the packed sentinel for no Shape row.

`first_field` is an index into the flattened field table, not a byte offset
into the XTC file. Names entries are first sorted by packed NamesId so the
tables are deterministic. `first_field` is the sum of `n_fields` for all
preceding entries.

## What is uploaded to and stored on the GPU

`GpuNamesSchema.to_device()` copies the two numeric tables to a
`DeviceSchema`:

```text
DeviceSchema.names   uint64[n_names, 6]
DeviceSchema.fields  uint64[n_total_fields, 5]
```

The device tables contain integer keys, not detector or field strings. The
current Python-facing `get()` resolves a string selector on the CPU and passes
the selected NamesId plus its field-table slice to `decode_fields`. The
current decoder consumes `DeviceSchema.fields`; `DeviceSchema.names` is
already uploaded for the fuller numeric device-side lookup ABI but is not yet
searched by these kernels.

The GPU also owns:

- the raw `uint8` byte buffer read by KvikIO;
- `dgram_info_gpu`, one row per complete indexed dgram;
- `shape_refs_gpu`, a fixed-capacity ShapesData-reference table;
- `shape_counts_gpu` and `walk_status_gpu`, one value per dgram;
- lazily allocated field-locator tables, cached by NamesId.

For driver printing and the Python debug API, `GPUDgramBatch` copies dgram
metadata, counts, statuses, and decoded locator rows to CPU NumPy arrays. That
metadata transfer is a prototype convenience; the event byte traversal and
field offset calculation occur on the GPU.

The CPU `raw_descriptors()` values `field_rel_offset` and `field_nbytes` are
not parser inputs. They can be removed from a production GPU path after the
GPU parser is trusted. In this driver they remain useful as an independent
oracle:

```text
expected device offset
  = indexed dgram offset in the GPU batch
  + CPU descriptor's field_rel_offset
```

## `GPUDgramBatch` structure

`GPUDgramBatch(data_gpu, schema, ...)` owns the raw GPU read and the parser
tables for one contiguous byte range. Its important state is:

```text
GPUDgramBatch
├── data_gpu                  CuPy uint8 buffer; offsets are relative to it
├── schema                    CPU GpuNamesSchema with strings and selectors
├── device_schema
│   ├── names                GPU packed Names rows
│   └── fields               GPU packed field rows
├── dgram_info_gpu            GPU uint64[n_dgrams, 8]
├── dgram_info                CPU debug copy
├── shape_refs_gpu            GPU uint64[n_dgrams, ref_capacity, 5]
├── shape_counts_gpu          GPU uint64[n_dgrams]
├── walk_status_gpu           GPU uint64[n_dgrams]
├── shape_counts              CPU debug copy
├── walk_status               CPU debug copy
└── _decoded[NamesId]
    ├── locators_gpu          GPU uint64[n_dgrams, n_fields, 11]
    └── locators              CPU debug copy
```

`batch[i]` returns a lightweight `GPUDgram` containing only its batch and
index. Its timestamp, service, and detector access are views into the batch:

```python
gpudgram = batch[3]
print(gpudgram.timestamp, gpudgram.service)

gpu_alg = gpudgram.get("xppcspad", 1, "raw")
if gpu_alg is not None:
    field = gpu_alg["arrayRaw"]
    print(field.type, field.shape, field.nbytes, field.device_offset)
    array_gpu = field.array
```

`field.array` aliases `batch.data_gpu`; it does not copy the field.

## Stage 1: indexing dgrams in the GPU byte buffer

The KvikIO read begins at the first byte after Configure, so offset zero in
`data_gpu` is a dgram boundary. `index_dgrams` is launched once with one block
and one thread. That thread iteratively advances through consecutive dgrams:

```text
offset = 0
while offset < input_nbytes and count < max_dgrams:
    root_extent = load_u32(data + offset + 20)
    total_dgram_size = 12 + root_extent
    validate total_dgram_size against the remaining input
    emit dgram_info[count]
    offset += total_dgram_size
```

The extra 12 bytes in `total_dgram_size` are the Sequence header preceding
the root XTC. The root XTC extent already includes its own 12-byte XTC header.
Consequently the complete dgram header is 24 bytes.

Each `dgram_info` row is:

```text
[device_offset, dgram_size, timestamp, env,
 service, damage, root_type, status]
```

`max_dgrams` is the output capacity and therefore the maximum number of
dgrams represented by this `GPUDgramBatch`. It does not control the KvikIO
read size; `--nbytes` does that. The indexer stops at the first of:

- the end of the supplied GPU byte buffer;
- an incomplete trailing dgram;
- an invalid dgram;
- `max_dgrams` complete dgrams.

The indexer reports `n_dgrams`, `index_status`, and `indexed_nbytes`.
`trailing_nbytes = data_gpu.nbytes - indexed_nbytes`. If status is `capacity`,
those trailing bytes may contain more complete dgrams; they are unindexed
because the batch's row capacity was reached.

For the example driver's `--nbytes 0x400000 --max-dgrams 16`, only 9,120 bytes
exist after Configure. The result is:

```text
gpu_read_bytes=9120
dgrams=16
indexed_bytes=9072
trailing_bytes=48
index_status=capacity
```

The fourth indexed dgram (`dgram=3`) begins at GPU-buffer offset 368. Its root
extent is 836 bytes, so its total size is:

```text
dgram_size = 12 + 836 = 848 bytes
```

Its `dgram_info` row is therefore:

```text
[368, 848, 4294967300, 0x0c000000, 12, 0, 0, 0]
```

Service 12 is `L1Accept`, root type 0 is `Parent`, and status 0 is `ok`.

## Stage 2: walking each XTC tree

After indexing, `walk_xtc` is launched once with one CUDA thread per complete
dgram. Threads process different dgrams in parallel; traversal within one
dgram is iterative and ordered.

XTC children are variable length. The next sibling begins at:

```text
next_child = current_child + current_child.extent
```

This dependency is why the baseline does not assign arbitrary byte ranges to
lanes. Detector payload bytes can resemble headers, so a parser cannot safely
discover sibling boundaries by scanning bytes in parallel.

The walker uses two fixed local arrays:

```text
cursor[depth]  offset of the next child in the current Parent
end[depth]     end offset of the current Parent
```

It starts at:

```text
depth = 0
cursor[0] = DGRAM_HEADER = 24
end[0] = dgram_size
```

The root XTC is itself a `Parent`, but it is represented by the initial
depth-0 range; the walker does not push the root. When it encounters a child
`Parent`, it first advances the current parent's cursor past that child, then
pushes the child's payload range at `depth + 1`. Reaching `end[depth]` pops
back to the enclosing parent. The fixed maximum is 16 cursor levels; trying
to push beyond it reports `capacity`.

Depth describes nested `Parent` containers. It does not count ShapesData
references. A direct ShapesData child of the root is found while `depth == 0`.
The `Shapes` and `Data` records inside a ShapesData are decoded later and do
not change the walker's depth.

On every `ShapesData`, the walker appends this five-column reference:

```text
[dgram_index, NamesId, device_offset, extent, damage]
```

`device_offset` is the absolute offset from the start of `data_gpu`, not an
offset relative to the current dgram. `shape_counts_gpu[dgram_index]` says how
many rows are valid. `max_shapes_per_dgram` is a fixed per-dgram capacity; it
defaults to at least the number of Configure Names entries.

### Real ShapesData references

The example's `dgram=3` has six direct ShapesData children:

| Dgram | NamesId | dgram-relative node offset | device offset | extent | Identity from Configure |
| ---: | ---: | ---: | ---: | ---: | --- |
| 3 | `0x100` | 24 | 392 | 164 | `xpphsd[0].raw` |
| 3 | `0x101` | 188 | 556 | 156 | `xpphsd[0].fex` |
| 3 | `0x102` | 344 | 712 | 92 | `xppcspad[0].raw` |
| 3 | `0x10a` | 436 | 804 | 164 | `xpphsd[1].raw` |
| 3 | `0x10b` | 600 | 968 | 156 | `xpphsd[1].fex` |
| 3 | `0x10c` | 756 | 1124 | 92 | `xppcspad[1].raw` |

For example:

```text
device offset for 0x10c = dgram offset 368 + node offset 756 = 1124
```

All six are direct children of the root:

```text
root Parent (depth 0 range)
├── ShapesData 0x100
├── ShapesData 0x101
├── ShapesData 0x102
├── ShapesData 0x10a
├── ShapesData 0x10b
└── ShapesData 0x10c
```

Across the first 16 dgrams in this example, maximum depth is zero and there
are no nested child-Parent records. This file tests multiple ShapesData
siblings but does not exercise `depth > 0`; a nested or synthetic fixture is
needed for that coverage.

## Stage 3: selecting and decoding a field

Tree walking discovers all ShapesData references, but it does not eagerly
decode every field. `gpudgram.get(detname, segment, algname)` performs a lazy
lookup:

1. `schema.find_all(...)` uses the CPU `_by_selector` dictionary to obtain all
   Configure schemas for the requested string tuple. The tuple is not assumed
   to map to a unique NamesId.
2. For each candidate, `_decode(names_schema)` allocates or reuses a locator
   table cached by NamesId.
3. `decode_fields` examines the valid ShapesData references on the GPU and
   ignores references whose NamesId does not equal the candidate NamesId.
4. A matching ShapesData is walked to find its immediate `Shapes` and `Data`
   children.
5. Fields are processed in Configure order. Scalars consume their element
   size. Arrays read dimensions from `shape_index`, multiply them by element
   size, and advance the running Data-payload offset.
6. The kernel emits one locator per schema field. Duplicate matching
   ShapesData records and malformed sizes/shapes produce explicit statuses.
7. If no candidate is present in this dgram, `get()` returns `None`. If one is
   present, it returns a `GpuAlgView`. More than one present candidate for the
   same selector is reported as an error.

Thus `get()` does some CPU control-plane selection, but the earlier walk did
not preselect a detector and the event's ShapesData presence and field
locations are resolved from GPU data. The first lookup of one NamesId launches
the decoder for all dgrams in the batch; later lookups reuse `_decoded`.

A locator row has 11 `uint64` columns:

```text
[field_key, type, rank, dim0, dim1, dim2, dim3, dim4,
 device_offset, nbytes, status]
```

For `xppcspad[1].raw.arrayRaw` in example `dgram=3`:

```text
matched ShapesData NamesId = 0x10c
field schema               = [9, 1, 2, 2, 0]
runtime shape              = (3, 6)
element size               = 2 bytes
nbytes                     = 3 * 6 * 2 = 36
device offset              = 1148
locator status             = found
```

The corresponding conceptual locator is:

```text
[9, 1, 2, 3, 6, 0, 0, 0, 1148, 36, found]
```

The CPU oracle reports `field_rel_offset=780` for this event. It agrees with
the GPU locator because:

```text
dgram device offset 368 + field-relative offset 780 = 1148
```

Again, the GPU parser independently calculates 1148 and 36. The driver reads
the CPU descriptor only afterward and then compares the 36 GPU-resident bytes
with the file bytes.

## Running the isolated driver

Run from the repository root in an environment containing the locally built
psana extension, CuPy, KvikIO, and a usable CUDA device:

```bash
python psana/psana/gpu/scripts/gpudgram_driver.py \
  psana/psana/tests/.tmp/xpptut15-r0014-s000-c000.xtc2 \
  --detname xppcspad \
  --segment 1 \
  --algname raw \
  --field arrayRaw \
  --nbytes 0x400000 \
  --max-dgrams 16
```

The representative output is:

```text
file=.../xpptut15-r0014-s000-c000.xtc2 configure_bytes=40608 \
gpu_read_bytes=9120 dgrams=16 indexed_bytes=9072 trailing_bytes=48 \
index_status=capacity
get=xppcspad[1].raw names_ids=0x10c
dgram=0 service=BeginRun timestamp=4294967297 shapes_data=3 walk=ok
dgram=1 service=BeginStep timestamp=4294967298 shapes_data=1 walk=ok
dgram=2 service=Enable timestamp=4294967299 shapes_data=0 walk=ok
dgram=3 service=L1Accept timestamp=4294967300 shapes_data=6 walk=ok
  arrayRaw: type=1 shape=(3, 6) nbytes=36 offset=1148 bytes-match
...
PASS: verified 10 matching dgrams
```

Important options:

- `--nbytes` controls how many contiguous bytes KvikIO requests after
  Configure, capped by the bytes remaining in the file.
- `--max-dgrams` controls index-table capacity, not read size.
- `--max-shapes-per-dgram` overrides the fixed ShapesData-reference capacity.
- Omitting `--field` verifies all fields in the requested schema.
- `--verify-max-bytes` limits CPU byte comparison for large fields. Larger
  fields still receive metadata checks.

The driver intentionally reopens each indexed dgram with CPU `dgram.Dgram`
only inside `_verify_dgram()`. That verification path must not be confused
with the GPU parser's operational inputs.

The schema unit test can be run without KvikIO data-path integration:

```bash
pytest -q psana/psana/tests/gpu/unit/test_gpudgram.py
```

## Error and capacity model

The kernels validate every header and extent against the logical containing
range. They expose statuses including:

```text
ok, found, not_present, partial_dgram, bad_dgram, bad_xtc, corrupted,
capacity, missing_shapes, missing_data, bad_shape, data_overflow, duplicate
```

The two main bounded resources are `max_dgrams` and
`max_shapes_per_dgram`; the tree stack is bounded by `MAX_DEPTH=16`. Capacity
exhaustion is reported rather than silently skipping data.

## Why start with one thread per dgram

An XTC parent's sibling chain is inherently ordered because each child's
extent locates the next header. The simplest safe baseline is therefore one
iterative walker per dgram, with parallelism across the dgrams in a batch.
This avoids C++ recursion, virtual callbacks, Python object construction, and
string comparisons even though the ordered traversal resembles CPU iterator
semantics.

Expected advantages are simple correctness, low coordination cost, and good
outer parallelism for large batches. Expected limitations are serial metadata
work within one dgram, warp divergence between different layouts, a fixed
local stack, and low occupancy for very small batches.

Payload size is not parser work: a multi-megabyte array still requires only
header, shape, and field-offset processing. The parser never scans every
payload byte.

## Cooperative comparison to add later

A cooperative design should preserve the same schema and locator contract so
that timing compares parsing strategy rather than a different API. It should
also preserve the ordered child-chain discovery instead of assigning
arbitrary byte ranges to lanes.

One possible two-stage design is:

```text
kernel 1: warp per dgram discovers ShapesData references
kernel 2: warp/block per reference decodes fields
          lane per field, tiled for more than 32 fields
          warp prefix sum computes Data-payload field offsets
```

An alternative is one block per dgram with warp 0 producing ShapesData
references into a bounded shared queue and other warps decoding them. That
avoids a second launch but adds synchronization, shared-memory capacity, and
error-propagation complexity.

The one-thread baseline is expected to do well for shallow layouts and large
batches. Cooperative decoding may help compound detectors with many fields,
many independent ShapesData records, small batches, or a future fused
locate-and-gather operation. This remains a benchmark hypothesis.

Parser-only measurements should exclude file I/O, RawKernel JIT compilation,
schema upload, and debug D2H metadata copies. Record batch size, number of XTC
nodes and fields per dgram, register/local-memory use, occupancy, and malformed
data checks. Correctness should cover nested Parents, missing/reordered
ShapesData, damage, truncated extents, variable shapes, mixed scalar/array
fields, and duplicate NamesIds before performance conclusions are used in the
DataSource path.
