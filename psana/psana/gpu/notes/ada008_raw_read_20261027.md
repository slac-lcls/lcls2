# Ada 008 hardware and raw-read bandwidth

Measured October 27, 2026, on **sdfada008**, Slurm job **42111297**.
The job completed successfully, exit 0, from **08:05:46 to 08:12:57 PDT**
(7 minutes 11 seconds). All 18 timed passes and final validation passed;
the private staged files were removed.
This is a storage-to-host test with regular files, without psana, CUDA data
processing, KvikIO, GDS, or host-to-GPU copies. It does not establish PR187/208
performance or a merge decision.

**Direct reads reached approximately 40.8 GB/s with 32 threads.** The later
two passes, after the observed GPU activity cleared, measured 40.772 and
40.751 GB/s (mean 40.762 GB/s). This is aggregate storage-to-host bandwidth.

Every pass started with **zero resident pages** in all five test files.
For every pass, md0 read exactly **85,899,345,920 bytes**, and the sum of its
six members' read counters matched that count exactly. Each SSD supplied
approximately 14.317 GB. All frozen file hashes matched before and after.
The final hardware inventory completed without command errors and showed all
ten GPUs idle with no GPU processes.

Concurrency matters: one synchronous reader does not expose the six-drive
array's aggregate throughput. At 32 readers each SSD contributes approximately
6.8 GB/s over the pass. We did not sweep beyond 32 readers or establish an
absolute maximum.

## Method

The exclusive allocation requested 72 logical CPUs, 32 GiB RAM and all ten
GPUs under `lcls:prjdat21`, normal QOS, Ada partition. Actual CPU affinity was
`0-23,36-71,84-95`, covering NUMA domains 0, 1 and 3. Threads inherited this
affinity and default NUMA policy; there was no per-thread binding or NUMA tuning.

The native pthread reader created five private, fully allocated 16 GiB files
under `/lscratch/monarin/ada-raw-read-42111297`: **80 GiB / 85.899 GB total**.
Preparation wrote deterministic pseudorandom blocks using direct I/O and fsync.
Each timed pass read all 81,920 blocks exactly once, with 1 MiB requests and
one synchronous `pread` outstanding per thread. A shared atomic counter assigned
increasing offsets across the files. This is a thread-count sweep, not a psana
BD topology or replay of its request pattern.

Conditions were direct I/O with 1/4/8/32 threads and buffered I/O with 1/32
threads, three repetitions each. Repetition 2 reversed the condition order.
Timing excluded file creation and cache preparation. It started immediately
before the main thread entered the start barrier and ended after joining all
workers; this includes any remaining worker setup at the barrier, descriptor
closes and thread teardown. Direct reads used aligned buffers and `O_DIRECT` to bypass the
Linux page cache. Before every pass, only these job-owned files were fsynced
and evicted with `POSIX_FADV_DONTNEED`; `mincore` checked residency. No global
cache drops were used. Disk counters bracketed each timed pass.

## Interpretation limits

The initial inventory found `/usr/bin/gpu` processes using seven GPUs, despite
the exclusive allocation. Their origin and exact exit time were not determined.
They were absent and all GPUs reported zero utilization and zero allocated
memory by 08:08:30 PDT. Subsequent timestamped observations are saved with the
results, including five-second observations during the final repetition. These
are sampled observations, not continuous proof of an otherwise idle node.
Treat repetition 1 as potentially affected by startup activity; the
later direct-read repetitions provide the better bandwidth estimate.

The buffered tests encountered the allocation's **32 GiB cgroup memory limit**
while streaming 80 GiB. At 08:09:22, `memory.peak` equaled the limit,
`memory.events:max` was 24,005, and direct page-reclaim counters were nonzero;
OOM and OOM-kill counts were zero. Their rates include page-cache allocation,
copying and reclaim. They are not an unrestricted buffered-I/O ceiling. A
buffered comparison with the planned psana campaign should use a comparable
memory allocation and request pattern, while retaining cold-cache checks.

The fastest passes last about two seconds. These measurements establish a
short streaming baseline, not sustained whole-drive performance. Disk counters
confirm reads reached the block devices; they do not establish that every byte
came from NAND rather than SSD-internal caches. No payload digest or detector
correctness test was performed.

## Conversion to application bandwidth

The [Ampere 013 qualification](ampere013_qualification_20261026.md) records
33,557,176 logical input bytes per event for run 387:

```text
payload GB/s = events/s * 0.033557176
300 events/s = 10.067 GB/s
320 events/s = 10.738 GB/s
```

Divide raw-read GB/s by 0.033557176 only to express an equivalent volume of
input per second. It is not a predicted psana rate: this reader excludes GPU
transfer, event handling, gathering, calibration, sharing and MPI costs.
In particular, aggregate six-SSD throughput is not bandwidth into one GPU.

Ada is a candidate for a same-node A/B/C comparison, but its L40S GPUs,
six-drive scratch and NUMA topology differ from Ampere 013. Run all variants
on the same physical node with matched settings and correctness checks;
do not compare Ada absolute rates directly against the A100 baseline.
