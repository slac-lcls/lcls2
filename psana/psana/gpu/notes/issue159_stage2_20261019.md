## Implementation

Commit `7f4288a5d` changes `_batched_gather_kernel` for uint16 and float32:

- Check the actual source address, including owner base and locator offset.
- Preserve the aligned typed-load path.
- Reconstruct unaligned values from individual bytes in the existing kernel.
  Float32 reconstruction preserves object bits through `__uint_as_float`.
- Preserve existing presence, shape and bounds validation and zero filling.
- Keep the same output allocation, launch count and thread-per-pixel mapping.
  No input repacking, additional full-image buffer or synchronization is added.

The focused tests cover every independent base/offset residue, exact allocation
tails, partial blocks, uint16 gain bits, float signed zero/subnormal/infinity/NaN
representations, invalid/absent rows, output reuse, stream dependencies and
constant launch count. The canonical parser/gather fixture now explicitly
retires completed aliases before checking released allocation charges.

Commit `f1688ef2c` adds that fixture cleanup and a standalone full-panel
Jungfrau gather benchmark. Production runtime is unchanged from `7f4288a5d`.
The benchmark validates every output pixel before and after timing, prepares
fixtures outside timing, warms compilation, and measures CUDA-event gather
latency for batch 1 and batch 20. A0/B0/B1 use the same harness. It does not
replace the planned staged four-BD comparison.

### Initial full-panel kernel timings

Same GPU/allocation, same harness, order A0/B0/B1 then B1/B0/A0. Each process
validates every output pixel before and after timing. Batch 20 is 640 MiB of
uint16 pixels (32 panels/event), measured with CUDA events; this does **not**
measure the four-BD pipeline.

| Case | First process median | Reverse-order median |
| --- | ---: | ---: |
| A0: frozen aligned | 4.0225 ms | 4.0193 ms |
| B0: candidate aligned | 4.1769 ms | 4.1728 ms |
| B1: candidate shifted one byte | 4.1859 ms | 4.1905 ms |

B0/A0 is **+3.84% / +3.82%**; B1/B0 is **+0.21% / +0.43%**.
All kernels use 30 registers. This is a repeatable safe-path kernel regression,
so stage 2 is not accepted. Early samples show clock warm-up; the controlled
follow-up increases untimed warm-up for every case and compares two small
branch-layout alternatives without changing frozen A or B.

### Branch-layout follow-up

Job **41319168** compares the original candidate and two alternatives with 256
untimed warm-up launches for every case. A/B installs remain unchanged;
experimental modules are loaded only by the benchmark process. All variants
validate the complete output before and after timing. The same process order
is reversed for the second comparison.

| Layout | Aligned overhead versus A, first / reverse | Unaligned median, first / reverse |
| --- | ---: | ---: |
| Original candidate | +3.84% / +3.82% | 4.1858 / 4.1871 ms |
| Early fallback return | +2.38% / +2.36% | 4.1285 / 4.1283 ms |
| Alignment branch around original pixel path | **+1.60% / +1.58%** | **4.1249 / 4.1246 ms** |

The final layout has aligned medians 4.0862 / 4.0861 ms; its unaligned increment
is about **0.94–0.95%**. It retains 30 registers, one launch and the same buffers.
Commit `7f29f0dc7` adopts this layout and adds an explicit benchmark warm-up
parameter (default 256). This reduces, but does not eliminate, the measured
safe-path overhead. The whole-pipeline impact has not been measured.
